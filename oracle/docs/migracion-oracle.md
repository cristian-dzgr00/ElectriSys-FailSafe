# Migración de ElectriSys a Oracle 23ai

Empezó como proyecto de la materia **Gestión de Base de Datos**: migrar el modelo relacional de ElectriSys (originalmente MySQL, ver [`database/`](../../database/), que queda como referencia histórica) a Oracle Database 23ai Free, con PL/SQL, triggers, vistas, roles/privilegios, índices con evidencia real de planes de ejecución, y backup/recovery.

**Actualización: esto ya es el motor real de la aplicación, no un ejercicio aparte.** El backend PHP completo (`backend/`) fue reescrito para conectarse a Oracle en vez de MySQL — `docker-compose.yml` ya no tiene ningún servicio MySQL. Ver la sección ["De ejercicio a motor real"](#de-ejercicio-a-motor-real-cambios-de-esta-fase) más abajo para el detalle de qué se ajustó del diseño original al conectarlo con la app viva.

Todo lo descrito en este documento fue **ejecutado y validado en vivo** contra una instancia real de Oracle 23ai Free (no es SQL sin probar) — evidencia y salidas reales más abajo.

## Mapeo de tipos MySQL → Oracle

| MySQL | Oracle | Motivo |
|---|---|---|
| `INT UNSIGNED AUTO_INCREMENT` | `NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY` | Equivalente moderno (12c+); `ON NULL` permite insertar un id explícito al sembrar datos |
| `VARCHAR(n)` | `VARCHAR2(n)` | Oracle no tiene `VARCHAR` estándar |
| `TEXT` | `VARCHAR2(4000)` | Ningún campo de texto libre del proyecto supera ese tamaño; evita el overhead de `CLOB` |
| `DECIMAL(p,s)` | `NUMBER(p,s)` | Directo |
| `TINYINT(1)` (booleano) | `BOOLEAN` | Tipo nativo desde Oracle 23ai — antes había que simular con `NUMBER(1)+CHECK` |
| `ENUM(...)` | `VARCHAR2(n) + CHECK (col IN (...))` | Oracle no tiene `ENUM` |
| `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | `TIMESTAMP DEFAULT SYSTIMESTAMP` | Directo |
| `... ON UPDATE CURRENT_TIMESTAMP` | Trigger `BEFORE UPDATE` | Oracle no tiene equivalente declarativo — ver `04_triggers.sql` |
| `JSON` | `JSON` | Tipo nativo desde Oracle 21c |

La tabla `heartbeat` (heartbeat de replicación de MySQL, para `pt-heartbeat`) **no se migró**: es infraestructura específica de la replicación MySQL primary/réplica del proyecto original (ver [`docs/asistente-nlp.md`](../../docs/asistente-nlp.md) y `ESTRUCTURA.md`), sin sentido en una instancia Oracle single-node.

## PL/SQL

Dos packages en `06_packages_plsql.sql`:

- **`PKG_VENTAS`** — `fn_generar_numero_venta` (usa la secuencia `seq_numero_venta` para generar `VT-2026-000123`), `registrar_venta` (recibe un `t_items_venta` — tabla anidada de objetos `t_item_venta` — calcula subtotal/total e inserta cabecera+detalle en una transacción) y `anular_venta`.
- **`PKG_REPORTES`** — `total_vendido`, `stock_valorizado`, `ranking_repuestos_mas_vendidos` (vía `SYS_REFCURSOR`).

**Validado en vivo:**
```sql
v_items := t_items_venta(t_item_venta(v_repuesto_id, 2, 35000, 0));
v_venta_id := pkg_ventas.registrar_venta(v_cliente_id, v_usuario_id, v_items);
-- Venta registrada, id=5 -> numero VT-2026-000001, subtotal=70000, total=70000
-- Stock de HP-1002: 12 -> 10 (el trigger trg_detven_descuenta_stock lo descontó solo)

pkg_ventas.anular_venta(v_venta_id);
-- Stock de HP-1002: 10 -> 12 (trg_ventas_anulada_restaura_stock lo restauró)
```

## Triggers (`04_triggers.sql`)

| Trigger | Evento | Qué hace |
|---|---|---|
| `trg_*_updated_at` (5) | `BEFORE UPDATE` | Simula `ON UPDATE CURRENT_TIMESTAMP` de MySQL en usuarios/proveedores/repuestos/clientes/cotizaciones |
| `trg_ventas_before_update` | `BEFORE UPDATE` | `updated_at` + incremento de `version` (control de concurrencia optimista) |
| `trg_detven_descuenta_stock` | `AFTER INSERT` en `detalle_ventas` | Descuenta stock del repuesto automáticamente |
| `trg_ventas_anulada_restaura_stock` | `AFTER UPDATE OF estado` | Repone stock si la venta pasa a `anulada` |
| `trg_repuestos_auditoria` | `AFTER UPDATE OF precio_venta, stock` | Inserta en `audit_log` — réplica a nivel de BD del patrón *Observer* que ya usa el backend PHP ([`AuditLogObserver`](../../backend/src/patterns/observer/)) |

**Validado en vivo, incluyendo el caso límite de sobreventa:**
```
Stock HP-1002 antes:            12
INSERT detalle_ventas (cant=3):  9   <- trg_detven_descuenta_stock
UPDATE ventas (cualquier campo): version 1->2, updated_at poblado
UPDATE ventas SET estado='anulada': stock 9 -> 12  <- restaurado
Intento de vender 9999 unidades:
  ORA-02290: restricción de control (CK_REPUESTOS_STOCK) violada
  ORA-06512: en TRG_DETVEN_DESCUENTA_STOCK
  -> la venta completa se revierte, el inventario nunca queda negativo
```

## Roles y privilegios (`08_roles_privilegios.sql`, `09_usuarios_demo_sysdba.sql`)

Los 3 roles de negocio de la tabla `ROLES` (admin/vendedor/dueño) se mapean a roles reales de Oracle con privilegios de objeto distintos — el vendedor nunca recibe `UPDATE`/`DELETE` directo sobre `REPUESTOS` (el stock solo cambia vía el trigger o un admin), y el dueño es de solo lectura + `EXECUTE` sobre `PKG_REPORTES`.

Se creó además un `PROFILE electrisys_profile` (bloqueo tras 5 intentos fallidos, vencimiento de contraseña a 90 días, `ora12c_verify_function` para complejidad mínima) y 3 usuarios de demostración: `electrisys_admin_demo`, `electrisys_vendedor_demo`, `electrisys_dueno_demo`.

**Validado en vivo (conectado como cada usuario real, no simulado):**
```
electrisys_vendedor_demo -> SELECT repuestos:        OK (23 filas)
electrisys_vendedor_demo -> DELETE repuestos:         ORA-41900: falta privilegio DELETE
electrisys_dueno_demo    -> SELECT vw_repuestos_...:  OK (2 filas)
electrisys_dueno_demo    -> INSERT clientes:          ORA-41900: falta privilegio INSERT
```

## Índices y planes de ejecución

Los índices de `03_indices.sql` replican los de MySQL, con una diferencia real encontrada durante la migración: `idx_repuestos_codigo` e `idx_clientes_identificacion` **no se crean** — Oracle ya genera un índice único implícito por las constraints `UNIQUE` correspondientes, y crear otro índice sobre las mismas columnas da `ORA-01408`.

Con datos de catálogo (23 repuestos, 12 clientes) el optimizador de Oracle elige *full scan* sin importar los índices — para una tabla tan chica es, correctamente, más barato que un acceso por índice. Para obtener evidencia real y no un plan trivial, se generó volumen sintético (`planes_ejecucion/generar_volumen_prueba.sql`: 8000 ventas + ~16000 líneas de detalle, con `trg_detven_descuenta_stock` deshabilitado temporalmente para no reventar el `CHECK` de stock durante la carga masiva — práctica estándar antes de una carga grande).

**Consulta 1 — `SELECT * FROM ventas WHERE cliente_id = 5`:**
```
ANTES (sin índice)                          DESPUÉS (con idx_ventas_cliente)
TABLE ACCESS FULL  VENTAS                   INDEX RANGE SCAN  IDX_VENTAS_CLIENTE
Cost = 29                                   TABLE ACCESS BY INDEX ROWID BATCHED
                                             Cost = 14   (-52%)
```

**Consulta 2 — total por repuesto de una venta (`GROUP BY` sobre `detalle_ventas`):**
```
ANTES (sin idx_detven_venta_repuesto)       DESPUÉS
TABLE ACCESS FULL  DETALLE_VENTAS           INDEX RANGE SCAN  IDX_DETVEN_VENTA_REPUESTO
HASH GROUP BY                               SORT GROUP BY NOSORT  (el índice ya entrega
Cost = 26                                    las filas ordenadas, se evita el sort)
                                             Cost = 3    (-88%)
```

El volumen sintético se eliminó después de capturar la evidencia — el esquema quedó de nuevo en el estado exacto de `05_seed.sql` (0 ventas). Para reproducir la evidencia: correr `generar_volumen_prueba.sql`, luego el `EXPLAIN PLAN` de cada consulta con y sin el índice (`DROP INDEX` / `CREATE INDEX` + `DBMS_STATS.GATHER_TABLE_STATS`).

## Backup y Recovery

**Elegido: backup lógico con Data Pump** (`expdp`/`impdp`), no RMAN físico — RMAN exige poner toda la instancia Oracle en modo `ARCHIVELOG`, un cambio de configuración global de la instancia local (afecta cualquier otro proyecto/PDB en esa misma instalación), así que no se activó unilateralmente. Queda documentado como referencia en [`backup/rman_backup_referencia.rman`](../backup/rman_backup_referencia.rman) para el escenario en que sí se disponga de una instancia dedicada.

**Backup real ejecutado** (`backup/backup_logico.sh`):
```
expdp electrisys/...@//localhost:1521/freepdb1
  directory=electrisys_backup_dir dumpfile=electrisys_backup_%U.dmp
  schemas=electrisys

. . "ELECTRISYS"."CATEGORIAS"       12 filas exportadas
. . "ELECTRISYS"."CLIENTES"         12 filas exportadas
. . "ELECTRISYS"."PROVEEDORES"      13 filas exportadas
. . "ELECTRISYS"."REPUESTOS"        23 filas exportadas
. . "ELECTRISYS"."REPUESTO_COMPATIBILIDAD"  42 filas exportadas
. . "ELECTRISYS"."VEHICULOS"        27 filas exportadas
...
Job "ELECTRISYS"."SYS_EXPORT_SCHEMA_01" terminado correctamente (2 min 13 seg)
```

**Restauración probada** importando el dump a un esquema `electrisys_restore_test` (remapeado, para no tocar el esquema real durante la prueba): las 15 tablas, 4 vistas, 2 packages, triggers e índices se recrearon con exactamente los mismos conteos de filas que el original. Único hallazgo: los tipos objeto (`T_ITEM_VENTA`/`T_ITEMS_VENTA`) fallan al recrearse bajo `REMAP_SCHEMA` (`ORA-02304`, OID embebido en el dump colisiona al cambiar de esquema) — limitación conocida de Data Pump con `TYPE` + remapeo, no un defecto del backup; en una restauración real al **mismo** nombre de esquema (el escenario real de disaster recovery, ver `backup/restaurar_logico.sh`) esto no ocurre. Como consecuencia, `PKG_VENTAS` quedó con advertencias de compilación únicamente dentro de ese esquema de prueba renombrado.

## De ejercicio a motor real: cambios de esta fase

Conectar este esquema (ya validado como ejercicio aislado) a la app PHP
que corre de verdad obligó a varios ajustes sobre el diseño original —
documentados acá para que quede claro qué y por qué se desvió:

- **`activo` (y columnas similares) pasaron de `BOOLEAN` nativo a
  `NUMBER(1)`.** El mapeo original usaba el `BOOLEAN` de Oracle 23ai (tipo
  nuevo, elegante), pero **todo** el backend PHP compara `activo = 1` /
  `WHERE activo=1` — comparar eso contra un `BOOLEAN` real da
  `ORA-00932`. Se priorizó no reescribir esa comparación en cada uno de los
  ~10 archivos que la usan.
- **`PKG_VENTAS.registrar_venta` se partió en dos.** La versión original
  recibía la venta completa (cabecera + todas las líneas) en un solo
  llamado, vía un parámetro de tipo colección Oracle (`t_items_venta`,
  `TABLE OF OBJECT`). Bindear tipos objeto/colección desde PHP (`oci8`) es
  la parte más frágil de la integración PHP↔Oracle — se cambió a
  `registrar_venta()` (solo cabecera, devuelve el id) +
  `agregar_item_venta()` (una línea por llamado, parámetros escalares
  simples). El backend hace el loop; los triggers de stock siguen
  funcionando igual sin importar si el INSERT vino de un loop o de una
  sola sentencia.
- **`registrar_venta` NO calcula impuesto/descuento.** Los recibe ya
  calculados desde PHP. `GestorVentas` (patrón Strategy —
  `PrecioEstandarStrategy`/`DescuentoVolumenStrategy`/`ExentoIvaStrategy`)
  ya decide esa regla de negocio antes de llamar a Oracle; el 19% fijo que
  se había puesto en un primer borrador de `agregar_item_venta` se sacó
  porque pisaba `ExentoIvaStrategy` (que cobra 0% IVA).
- **Se agregaron `PKG_VENTAS.listar_ventas`, `buscar_venta_por_id` y
  `PKG_REPORTES.resumen_hoy`** (vía `SYS_REFCURSOR`) — el diseño original
  no cubría el listado paginado+filtrado, el detalle con líneas, ni el
  resumen diario global que ya usaba el backend PHP.
- **`p_desde`/`p_hasta` de `listar_ventas` son `VARCHAR2`, no `DATE`.**
  Bindear un `DATE` desde PHP vía `oci8` depende del `NLS_DATE_FORMAT` de
  sesión (no necesariamente `'YYYY-MM-DD'`) — más predecible convertir con
  `TO_DATE(p_desde, 'YYYY-MM-DD')` adentro del package.
- **`consultas_asistente.util`** (columna de feedback 👍/👎, agregada del
  lado MySQL en `database/schema_v4_migration_feedback.sql`) y el índice
  `idx_consultas_fecha` faltaban en el DDL original — se agregaron acá.
  `texto_consulta` también se amplió a `VARCHAR2(4000)` (estaba en 1000,
  contradiciendo la propia regla de mapeo del documento).
- **`vw_repuestos_compatibles`** se amplió con `descripcion`,
  `precio_venta`, `categoria` y `proveedor` — el backend
  (`GET /api/repuestos/buscar-compatibles`, que usa el asistente NLP)
  necesitaba esas columnas y la vista original no las traía.
- **Capa de conexión PHP:** se escribió un envoltorio delgado
  (`backend/src/models/OciConnection.php` + `OciStatement.php`) que imita
  la superficie de `PDOStatement` (`prepare`/`execute`/`fetch`/`fetchAll`)
  sobre la extensión `oci8` — así las ~40 queries del backend solo
  necesitaron cambiar texto SQL (paginación `OFFSET/FETCH`, `RETURNING id
  INTO` en vez de `lastInsertId()`, `ORA-00001` en vez de detectar
  "Duplicate" en el mensaje de error de MySQL), no su forma de invocación.
  También resuelve algo que rompía silenciosamente al principio: `oci8`
  devuelve **todas** las columnas `NUMBER` como string — se castean a
  int/float por metadata real de columna (`oci_field_type`), no por
  heurística, para que el JSON de cada endpoint siga siendo numérico como
  antes (el microservicio NLP en Python, por ejemplo, comparaba
  `stock > 0` y explotaba con `stock` como string).
- **Se retiró el failover primary/réplica de `Database.php`**
  (`$usingReplica`/`isWritable()`) — Oracle 23ai Free no soporta Data
  Guard/RAC (son features Enterprise), así que la topología quedó de una
  sola instancia. Se retiró también `ventas.pendiente_sync` (existía solo
  para reconciliar escrituras con la réplica MySQL).
- **`docker/Dockerfile.backend`** pasó de `php:8.2-fpm-alpine` a
  `php:8.2-fpm-bookworm` (Debian): el Oracle Instant Client no tiene
  binarios oficiales para musl-libc (Alpine), solo glibc. Se fijó a
  `bookworm` explícitamente (no el tag genérico `php:8.2-fpm`, que ya
  apunta a Debian 13 "trixie" y renombró `libaio1`→`libaio1t64` con un
  SONAME distinto al que espera el Instant Client).
- **Imagen del contenedor: `gvenzl/oracle-free:23-slim`** (comunitaria,
  no la oficial de Oracle) — soporta `ORACLE_PASSWORD`/`APP_USER`/
  `APP_USER_PASSWORD` como variables de entorno, igual de simple que la
  imagen oficial de MySQL, y trae healthcheck propio.

## Limitaciones conocidas

- No se activó `ARCHIVELOG` ni se probó RMAN físico (ver justificación arriba).
- El restore de prueba usó un esquema remapeado por seguridad (no se tocó el esquema real `electrisys`); esto ocultó el único problema real de Data Pump con `TYPE`+`REMAP_SCHEMA`, documentado arriba pero no reproducido en una restauración al mismo nombre.
- El esquema `electrisys_restore_test` quedó creado en la instancia como evidencia de la prueba de restauración — se puede eliminar con `DROP USER electrisys_restore_test CASCADE;` si no se necesita conservar.
